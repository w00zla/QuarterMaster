# Catalog data sources

Research, spike results and implementation of the game catalog (materials, harvestables, blueprints, texts).
As of 2026-10-04, game build `4.10.1-LIVE.12660092`.

---

## Decision

- **Primary source: own extract** from the local `Data.p4k` via StarBreaker (`local/starbreaker`, MIT, v0.3.2).
- **Reference / fallback: [StarCitizenWiki/scunpacked-data](https://github.com/StarCitizenWiki/scunpacked-data)** (ScDataDumper output, one commit per patch, no LICENSE).
- **Extractor and importer in TypeScript.** The extractor runs locally per patch; the importer is a CLI with metrics, safeguards and dry-run.
- **Contract = our own snapshot format** (versioned: `schemaVersion` + game build). Extractor implementations are swappable behind it.
- **DB access: Drizzle** (schema in TS, migrations generated by `drizzle-kit`).
- **Everything conceivably useful goes into the DB:** raw records as `jsonb` next to the normalized tables, complete game texts of all languages. Quality bands are stored but not used by the app yet.
- **Ores** are in the catalog (`resource.is_ore`), but **not stock** (since migration `0025`: refinery jobs hold the refined materials). Recipes take the refined resource only.
- **Blueprint sources derived from the contract records** (since 2026-10-21, snapshot schema 4): which mission or event tier hands out which reward pool, with the mission's texts and conditions; see "Blueprint sources". The contract records themselves are not kept raw (96 MB).
- **Externally maintained `global.ini` files** (community translations) can be imported as additional text sources with a priority.
- Repo is private for now.

```
[local, per patch]                                         [bot repo]
Data.p4k ─starbreaker dcb─> raw JSON ─extractor─> catalog-<build>.json ─import CLI─> Postgres
                                          ▲
                   scunpacked-data: reference for tests + fallback source
```

### Not used
- **Wiki API** (`api.star-citizen.wiki/api/blueprints`): fine for exploring and `web_url` links, but fed from the same data as scunpacked. Its list endpoint links some ingredients to the *ore* commodity while `resource_type_uuid` is the *refined* resource.
- **UEX**: API key, prices/commodities, no recipes.
- **sc-craft.tools**: no API.
- **FleetYards**: GPL, derived from the same game data, extra hop.
- **Own DCB parser**: no. StarBreaker already does it.

## Extraction (StarBreaker)

```sh
export SC_DATA_P4K=".../StarCitizen/LIVE/Data.p4k"
starbreaker p4k extract -o out --filter '**/Game2.dcb'                 # ~317 MB, <1 s
starbreaker p4k extract -o out --filter '**/global.ini'                # all languages
starbreaker dcb extract --dcb out/Data/Game2.dcb -o rec --format json \
  --filter 'libs/foundry/records/crafting/**'                          # 1917 records
starbreaker dcb extract ... --filter 'libs/foundry/records/resourcetypedatabase/**'
starbreaker dcb extract ... --filter 'libs/foundry/records/entities/scitem/**'   # 24064 records
starbreaker dcb extract ... --filter 'libs/foundry/records/starmap/**'           # 2073 records
starbreaker dcb query --dcb ... 'CraftingBlueprintRecord'              # dump by type
```

- `--filter` is a **path glob on the record file path**, not on the record name. Wildcards inside a path segment match nothing (`**/*refin*` → 0 records); whole segments work (`**/refinery/**`).
- The game build is in `build_manifest.id` next to `Data.p4k` (`RequestedP4ChangeNum`).
- Float output is full precision (e.g. `0.2233005`).

### Blueprint structure

```
CraftingBlueprintRecord (_RecordId_ = blueprint UUID)
└ blueprint
  ├ category → BlueprintCategoryRecord
  ├ processSpecificData: CraftingProcess_Creation { entityClass: <file path of output entity> }
  └ tiers[]                                   always 1 today, model as array
    ├ recipe.costs
    │ ├ craftTime {days,hours,minutes,seconds}
    │ ├ mandatoryCost: CraftingCost_Select "ASPECTS" { count, options[] }   root
    │ │   └ options[]: CraftingCost_Select = slot { nameInfo.debugName, count, context[modifiers], options[] }
    │ │        └ options[]: CraftingCost_Resource { resource → ResourceType UUID, quantity.standardCargoUnits, minQuality }
    │ │                     CraftingCost_Item     { entityClass → entity path, quantity (count), minQuality }
    │ └ optionalCosts[]                         always empty today
    └ research { unlockRequirements, researchCosts }   present on 916, all null today
```

### Location structure

```
StarMapObject (_RecordId_ = location UUID)
├ name, description            loc keys (@LOC_UNINITIALIZED / @LOC_PLACEHOLDER common)
├ parent                       file path of the parent StarMapObject (null for systems/stars)
├ type                         → inline StarMapObjectType in starmapobjecttypes.json
├ navIcon                      Station | LandingZone | Outpost | Moon | Planet | Star | Default
├ hideInStarmap                hidden objects (jump points, internal stations, …)
├ respawnLocationType          None | Hospital | Other | Prison | …
├ amenities[]                  references to StarMapAmenityTypeEntry (starmapamenitytypes.json, not extracted:
│                              only the UUIDs are in the record), e.g. "Commodity Trading - Freight Elevator"
│                              a783bfb9-…, "- Loading Dock" 02905cad-…, "Refinery" 7618a59c-…, Hospital, Garage,
│                              Landing Pad S–XL, Hangar S–XL
└ assetManagerLocationParams   preview images of the asset manager; NOT a storage flag
```

- Hierarchy: system star → planet/moon → landing zone/outpost; orbital and Lagrange stations hang directly below the star (`HUR-L1 Green Glade Station · Stanton`). Stanton, Pyro and Nyx are included.
- **Selection rule for storage locations** (applied by the app, the DB keeps everything; `selectableLocationSql` in `src/stock/service.ts`): `navIcon` `Station` or `LandingZone`, or the freight elevator amenity (a location inventory), not `hideInStarmap` (the Onyx facilities `*_ASD_Delve_Facility_*` are hidden and stay out), plus a fixed key list; an English name. Build 12913470: 152 (69 stations/landing zones, 73 outposts by amenity, 10 by the list). The amenity is incomplete: 10 places where Game.log shows the freight manager's warehouse opened lack it (Wikelo Emporium ×3, the 3 junk sites, QV Logistics Station `Nyx_Kaboos` (hidden), Shubin SMCa-6/-8, Vivere OLP; checked 2026-10-19), hence the list. Build 12660092 (stations/landing zones only): 79 candidates, 76 with an English name, 37 with a German game text.
- Quirks:
  - Duplicate names in different systems: `Stanton Gateway`, `Pyro Gateway`, `Nyx Gateway` exist twice each → labels need the system/parent.
  - Names without any text: `@RR_P1_L4`, `@RR_P3_L2`, `@RR_P6_L1` (Pyro stations) → fallback to the key.
  - `@LOC_UNINITIALIZED` (text `<= UNINITIALIZED =>`) on 60 names → treated as a sentinel (`NULL`).
  - **No refinery flag in the DataCore** (except the star map amenity "Refinery", found 2026-10-19, not used). Refinery terminals are entities (`EntityClassDefinition.Refinery` with `EntityComponentRefineryParams`) placed in the level object containers (socpak), not referenced from star map records. Only 6 Stanton station descriptions mention refining (incomplete). `starmap/pu/station/refinery/refinery_0001` is a WIP placeholder. Refining methods: `refiningprocess/*` (`RefiningProcess`) carry only `refiningSpeed` (Fast/Normal/Slow), `refiningQuality` (Careful/Normal/Wasteful) and the name key (9 methods; the record `RefineNormal` is Normal/Wasteful = Cormack); no factors, times or costs. `EntityComponentRefineryParams` is empty. Yields, times, costs and location bonuses are server-side: the app takes refinery locations and yield bonuses from UEX (`ext` schema, see `docs/ext.md`).
  - `assetManagerLocationParams` is set on 117 objects, Stanton only, including Lagrange points and moons → unusable as "has storage".

### Blueprint sources

Where a blueprint comes from (`src/catalog/extract/sources.ts`, snapshot `blueprintSources`, table
`catalog.blueprint_source`). The reward pools are the only link between blueprints and the game: a binary
count of every pool and blueprint GUID in `Game2.dcb` (4.10.2) matches the references found here exactly, so
the DataCore has no other source (no shops, no items). Server-side unlocks are not visible.

```
ContractGenerator.generators[] (handler)        required_active_scenarios, defaultAvailability.prerequisites,
│                                               contractParams (Title), factionReputation, minStanding
└ contracts[] | introContracts[] | legacyContracts[] | PVPBountyContract[]
  ├ notForRelease                               true: left out (85 BP contracts, e.g. the RDC boss pool)
  ├ template → contractDisplayInfo              type → MissionType (LocalisedTypeName), illegal
  ├ paramOverrides.stringParamOverrides         Title (else the handler's), missionTypeOverride
  ├ additionalPrerequisites                     Locality → MissionLocality.availableLocations (systems),
  │                                             Location (bound to a star map object), CompletedContractTags (chain)
  ├ minStanding → SReputationStandingParams     displayName (rank), minReputation
  └ contractResults.contractResults[]           BlueprintRewards: blueprintPool, chance, missionResults
                                                ([0] completed, [1] accepted: derived from patterns, unnamed)
ScenarioProgress (contracts/contractscenarios)  …tierRewards[] (STierReward): minPoints, blueprintPool[]
BlueprintPoolRecord.blueprintRewards[]          blueprintRecord, weight (all 1.0 in 4.10.2; duplicates add up)
```

- One row per blueprint, contract (or event tier) and pool: `kind` `mission`/`event`, `weight` of the pool's
  total `pool_weight` (the game picks one entry by weight), the contract's `contract_id` (an id inside the
  generator record, not a record id) and `contract_key` (debug name), `title_key`, `mission_type_key`,
  `faction_uuid`/`faction_name_key`, `min_rank_name_key`/`min_reputation`, `locality_uuids`/`location_uuids`
  (star map objects: the locality lists systems, planets, Lagrange points, stations as the game does; the
  system follows from their parents), `requires_previous`, `illegal`, `chance`, `on_accept`, `event_key`, `min_points`.
- **Event:** an event tier (`kind` `event`: RoX, ORS) or a contract whose required scenario is started by hand
  (`schedule.enabled: false`: ORS). RCD's scenarios run all the time and do not count. `event_key` is the
  scenario's record key without `_MissionScenario`/`_ScenarioProgress`. Whether an event runs is not in the
  data (CIG starts it on the server).
- Left out: contracts not for release; sub-contracts (no rewards of their own); `MissionModifier_TemporaryBlueprint`
  (2 ORS contracts, a temporary mission item; `ORS_Cr_Large` hands out the same pool regularly); pool entries
  without a blueprint (2, `ASD2C`, `InterSec_Patrol`: an anomaly, the game's handling is unknown).
- Build 12913470: 7730 rows, 701 contracts, 703 blueprints with a source (678 by mission, 25 RoX tiers, 1 ORS);
  29 illegal contracts; titles on 7695 of 7705 mission rows. 26 blueprints sit in pools nothing references
  (17 ORS "SecondWind" pools: the ORS tiers have badges but empty pool lists), 9 only in unreleased contracts.
- Cross-checked against scmdb.net (same build, 2026-10-21): pools, members and the contracts per blueprint
  agree completely; SCMDB lacks the RoX tiers and drops the 2 null entries. It annotates CIG data errors but
  keeps the values.

## Implementation

```
Data.p4k --StarBreaker--> DataCore records (JSON) --normalize--> snapshot (.json.gz) --catalog:import--> Postgres "catalog"
external global.ini ------------------------------------------------------------------loc:import-----> Postgres "catalog"
```

Commands (`pnpm catalog:extract`, `catalog:import`, `loc:import`): `CLAUDE.md`. Both imports also run from the
admin web UI (upload, dry run first), using the same functions as the CLIs.

- **The snapshot format (`src/catalog/snapshot.ts`, Zod) is the contract** between extractor and importer.
  It is versioned via `SNAPSHOT_SCHEMA_VERSION` (currently 4, since the blueprint sources; an older snapshot must be extracted again);
  extractor implementations are meant to be swappable behind it (scunpacked-data is the documented fallback
  source). `src/catalog/import/load.ts` reads and checks a snapshot (gzip detected by content) for the CLI
  and the API.
- **Extractor** (`src/catalog/extract/`): `cli.ts` shells out to the StarBreaker CLI (`p4k extract` for
  `Game2.dcb` + all `global.ini`, then `dcb extract --format json` for selected record subtrees; `--filter`
  globs match record *file paths*). `RecordStore` lazily reads records by lower-cased path; references between
  records are `file://…/libs/foundry/records/…` paths resolved via `refPath()`. `normalize.ts` must never crash
  on unexpected shapes: unknown types, `null` list entries and dangling references become `anomalies` in the
  snapshot. Items and manufacturers are included when referenced by a blueprint, plus every named ship item
  (`entities/scitem/ships/`, no `template` in its path) whose type is in `COMPONENT_TYPES`
  (`src/catalog/components.ts`): looted and bought ship components are stock too (2026-10-18). Locations are
  all `StarMapObject` records below `starmap/` (parent resolved to a UUID, type name from the inline types in
  `starmapobjecttypes.json`). Game build/channel come from `build_manifest.id` and the install folder name,
  not from a version string (the manifest has no "4.10.1").
- **Catalog import** (`src/catalog/import/`): `plan.ts` is pure (snapshot → rows with content hashes,
  integrity check, diff, safeguard evaluation) and unit-tested without a DB; `apply.ts` runs everything in one
  transaction under a Postgres advisory lock (`IMPORT_LOCK`, shared with the localization import). A dry run
  executes the full import and then calls `tx.rollback()`; `noop`/`blocked` results also roll back. CLIs exit
  0 (imported/dry run/no-op), 1 (error), 2 (blocked by a safeguard).
- Tests: `test/fixtures.ts` builds synthetic DataCore records (no real game data) and runs them through the
  real normalizer; the resulting snapshot feeds both the pure tests and the DB integration tests.

| Path | Content |
|---|---|
| `src/catalog/extract/` | extractor: StarBreaker wrapper, record store, `global.ini` parser, normalizer, CLI |
| `src/catalog/snapshot.ts` | snapshot format (Zod), `SNAPSHOT_SCHEMA_VERSION` (4) |
| `src/catalog/import/` | catalog import (`load.ts` read + check, `plan.ts` pure logic, `apply.ts` DB, `cli.ts`), localization import (`loc-import.ts`, `loc-cli.ts`) |
| `src/catalog/labels.ts` | app texts (key prefix `qm_`), category groups, item type/class keys, derived names |
| `src/db/schema/catalog.ts` | Drizzle schema, Postgres schema `catalog` |
| `drizzle/` | migrations: `0000_catalog.sql` (schema + seed of the app texts), `0001_location.sql` |
| `local/` (gitignored) | `starbreaker` binary, `snapshots/`, `localization/<source>/global.ini`, `work/` |

### Database (`catalog` schema)

- `import`: one row per catalog import (build, channel, label, snapshot hash, extractor versions, summary, anomalies).
- Global for all guilds; migrations in `drizzle/`.
- Entities `manufacturer`, `item`, `resource`, `blueprint_category`, `crafted_property`, `quality_quantization`, `blueprint`, `location`, `raw_record`: UUID primary key plus `content_hash`, `first_seen_import_id`, `last_seen_import_id`, `retired_at`. **Never deleted**; missing entries get `retired_at` (cross-checked against the diff), reappearing ones are revived. Guild data references catalog UUIDs and survives retirement.
- `raw_record` keeps every extracted DataCore record as `jsonb`, so new game data can be normalized later without re-extracting (the component base values are read from it, `src/stock/component-base.ts`).
- Quantities are `NUMERIC` and passed to Postgres as strings.
- Storage locations are selected by the app (stations, landing zones and places with a freight elevator, see "Selection rule for storage locations"; the amenity is read from `raw_record`).
- `location`: every `StarMapObject` with `parent_uuid` (no foreign key: rows of one import reference each other in any order; the integrity check ensures every parent is in the snapshot), `type`, `nav_icon`, `hide_in_starmap`, `respawn_location_type`. Names via `name_key`.
- Recipe tables `blueprint_tier` (incl. `required_slots` for "N of M slots"), `blueprint_slot` (modifiers as `jsonb`), `blueprint_input` (`kind` resource/item, `quantity` as `NUMERIC`): replaced as a whole when their blueprint changes.
- `blueprint_source` (migration `0029`): the snapshot's `blueprintSources`, numbered per blueprint (`source_index`), replaced as a whole on every import (derived, nothing references it). See "Blueprint sources".
- Localization:
  - `localization_source` (source, lang, priority, origin, hash, key count): `game` = priority 0, written by the catalog import; external sources default to 100.
  - `localization` (source, lang, key, value).
  - View `localization_effective`: per language and key the text of the highest-priority source. Priority applies per source, not per key.
  - Source `app` (priority 1000): the app's own texts for names the game lacks, keys with the reserved prefix `qm_`: blueprint category groups (`qm_blueprint_category_<group>`, the category without its size: `VehicleComponentS1` → `VehicleComponent`) and item classes (`qm_item_class_<class>`, e.g. `energy_laser`). Seeded by the migration (24 texts per language: de/en), maintained via the admin UI later. Never taken from a `global.ini`.
- Loc keys are stored lower case without `@`; `LOC_EMPTY`/`LOC_PLACEHOLDER`/`LOC_UNINITIALIZED` become `NULL`; texts have literal `\n` converted and "TRANSLATION NOT FOUND" placeholders removed. Some items have no name in any language → display code falls back to `class_name`.
- Display names (`src/catalog/labels.ts`): game key `item_type<type>`/`item_subtype<subtype>` for types; `qm_blueprint_category_<group>` (`blueprintCategoryGroup`) and `qm_item_class_<normalized class>` for app texts; otherwise a name derived from the technical key (`labelFromKey`). SQL helpers (`locText`, `categoryText`, `itemClassText`) in `src/db/query.ts`.
- `item.grade_letter` (A–D) and `item.item_class` (English, e.g. `Military`, `Energy (Laser)`): parsed by the extractor from the English description, the only place the game states them. Only ship components have a grade; personal weapons have weapon classes.

### Import safeguards

- Catalog import: one transaction with advisory lock; dry run = full run + rollback. Hard errors on schema/integrity failures (dangling references, duplicates). Identical snapshot = no-op. Blocked (exit 2, overridable): downgrade (`--allow-downgrade`), >10% of an entity retired or >50% changed (`--force`, ratios configurable). Retire count is cross-checked against the diff.
- Localization import: same lock; identical texts + priority = no-op. Blocked: >50% of the source's texts would disappear, <50% of the file's keys known to the game (wrong file). Source names `game` and `app` are reserved; keys with the prefix `qm_` are skipped. UTF-8 and UTF-16 with BOM.
- Both also run from the admin web UI (file upload, dry run first; Import only after a passed dry run of the same file and options).

## Spike result: own extract vs. scunpacked-data (same build 12660092)

Throwaway script, not in the repo. Result:

- **Same 1607 blueprint UUIDs**, same output UUIDs, same craft times, same slot modifiers.
- **Same availability:** 8 default, 732 in ≥1 reward pool, **867 with no known source**.
- Differences:
  - 10× output name with trailing whitespace in the loc string → trim.
  - 3× root `count` < number of slots (`thp_light_legs_01_01_{01,03,12}`: 2 of 3 slots). scunpacked nests this as an `ASPECTS` group → **our model needs "N of M slots" at the root level**.
  - 3× `slaver_armor_medium_arms_01_01_{01,13,15}`: Ouratite **0.04 SCU (DCB via StarBreaker) vs 0.046 (scunpacked + Wiki API, unchanged since 4.7)**. Cause unclear; StarBreaker JSON and XML agree on 0.04. → check in game.

- Two modifier range types: `…ValueRange_Linear` (`modifierAtStart/End`) and `…ValueRange_LinearIntegerAdditive` (`additiveModifierAtStart/End`).
- `null` entries inside lists: 466 value ranges, 5 contexts, 2 reward pool references.
- `BP_CRAFT_COOL_S04_CNOU_Pioneer` has no output entity (`entityClass` null) → skip and report.

## Domain facts for the schema

- **Stable IDs:** blueprint UUIDs and keys did not change across 4.7 → 4.8 → 4.9 → 4.10.1 (scunpacked history). Anchor on **UUID**, store the key alongside.
- **Blueprints disappear:** 11 removed between 4.7 and 4.10 (+574 added). Catalog entries are **retired, never deleted**.
- **Two input kinds:**
  - `resource`: refined material in SCU, fractional (smallest seen 0.015 SCU in recipes, 0.005 in dismantle returns). 26 resources used in recipes.
  - `item`: harvestables etc., counted in pieces (e.g. Hadanite ×7).
- **Recipes take refined material, not ore.** Ore and refined material are separate records with separate UUIDs (`ResourceType.refinedVersion`).
- **Quality:** raw value 0–1000 per input; `minQuality` per input; modifier curves per slot.
- **Quality bands exist** (`crafting/qualityquantization`): 8 bands with **identical boundaries for all 63 materials** (0–399, 400–599, 600–699, 700–799, 800–899, 900–949, 950–998, 999–1000), but a **`mappedValue` per material and band**. The meaning of `mappedValue` is unverified (quantized quality?). Band labels (S/A/…) were not found in the data.
- **Localization:** `global.ini` exists for 11 languages. German covers commodity names (e.g. "Borase (Erz)") and ~85% of blueprint output names (1357/1606), **no crafting slot names**. Fallback to English is needed.
  - Non-English files contain ~2900 placeholders each (`! GERMAN_(GERMANY) TRANSLATION NOT FOUND FOR LOCID: … !`); the extractor skips them.
  - Line breaks are written as a literal `\n`; the extractor converts them.
  - 4 blueprint outputs have no name even in English (e.g. `COOL_AEGS_S04_Javelin_SCItem`) → the app needs a fallback to `class_name`.
  - The community file (variant "Hybrid") keeps item names English on purpose ("Borase (Ore)" vs. the game's "Borase (Erz)").
- **Crafted stats** (checked 2026-10-18 on build 12881860, ship components):
  - A slot's modifier changes one crafted property (`CraftingGameplayPropertyDef`) by quality: `Linear` ranges are **factors** (typically 0–500: 0.8→1, 501–1000: 1→1.2; Q500 = no change), `LinearIntegerAdditive` ranges are **steps** in constant bands (only `GPP_ItemResource_PowerGeneration`, "Power Pips": −1/0/+1 per slot). Several slots may change the same stat (a cooler's coolant: COOLANT 0.85–1.15 and PUMP IMPELLER 0.95–1.05).
  - Per component type: Cooler = Coolant Rating + Integrity, PowerPlant = Power Pips + Integrity, Shield = Max. Shield Strength + Integrity, QuantumDrive = Quantum Speed + Fuel Requirement (flat 1.0) + Integrity, Radar = two aim assist distances + Integrity, ship weapons and mining lasers = Impact Force + Integrity, tractor/salvage heads 3–4 own values. The names match the game's tooltip ("Coolant Rating: 22.00, Integrity: 110.00").
  - The **absolute values** need the item's base value, which is not in the blueprint but in its `raw_record`, at a different path per property (`src/stock/component-base.ts`, verified against the user's inventory tooltips of 2026-10-18): Integrity `Components[SHealthComponentParams].Health` (HeatSafe 110, Blizzard 1800, Atlas 200, CoverAll 660), Coolant Rating `Components[ItemResourceComponentParams].states[].deltas[].generation(resource Coolant).resourceAmountPerSecond.standardResourceUnits` (HeatSafe 22, Blizzard 60; the property's display scale 1e-6 does not apply to the record's value), Power Pips the same with resource Power → `.units` (Regulus 16; tooltip not seen yet), Max. Shield Strength `SCItemShieldGeneratorParams.MaxShieldHealth` (CoverAll 10560), Quantum Speed `SCItemQuantumDriveParams.params.driveSpeed` × 1e-6 (Atlas 259054500 → "259.05 Mm/s"), Quantum Fuel Burn `SCItemQuantumDriveParams.quantumFuelRequirement` × 1000 (Atlas 0.007546 → "7.55 per Km"), radar `SCItemRadarComponentParams.aimAssist.distanceMax/MinAssignment` (tooltip not seen yet). Weapons (Impact Force: displayed as a percent change of the base per its display transformation), tractor and salvage heads: no path, their tooltip format is unknown. The web app stores stats as the crafting check shows them (percent change / steps); the companion's components scan converts the tooltip's values with these bases.
  - **How several slots on one stat combine is unverified**: the crafting check multiplies the factors and adds the steps (as erkul.games and sc-craft.tools do); SC Crafter, the Citizen Starter Guide blueprint finder, scblueprintfinder and SC-Toolbox's Craft Database add the deltas instead. None measured it in game; at the current spans the results differ by 1–2 %. One craft decides: an IcePlunge cooler (base coolant 22) with both slots at Q1000 shows 26.57 (product) or 26.40 (sum).
  - Materials below Q500 (the only ones that lower a stat) cannot be used for crafting at the moment (user, 2026-10-18), although recipe inputs have `minQuality` from 0.
  - Display transformations (`CraftingDisplayTransformation_*`: `Scale`, `ConvertValueToFactorOfBaseValue`, `ConvertFactorToPercentChange`) are documented nowhere; known scales: coolant 1e-6, quantum speed 1e-6.
- **Ship components beyond the blueprints** (2026-10-18, build 12913470 / 4.10.2): the snapshot takes every named ship item (`entities/scitem/ships/`, no `template` in the path) whose `AttachDef.Type` is in `COMPONENT_TYPES` (`src/catalog/components.ts`), 781 items on top of the 1614 blueprint-referenced ones. `Turret` (249) and `TurretBase` (131) include the turrets built into ships (remote cameras, AI turrets) the player never holds; `Missile` (65) and `MissileLauncher` (149) the ship-fitted ones too. Event items like the "Ardor-3 Salvaged Repeater" are `WeaponGun` items and now in the catalog without stats (no blueprint, no bounds).
- **Prepared but unused by CIG:** `tiers[]` (always 1), `optionalCosts` (always empty), `research` (always null). The schema should not block them.
- **Catalog is global**, not per guild. One import affects every server → safeguards matter.
