## Project

Discord bot for Star Citizen players and orgs to manage materials (stock) and blueprints. Multi-guild (one Discord server = one org), German/English. Product requirements, role model and localization rules: `docs/requirements.md`. Ideas adopted from another bot (concepts only, no code — that repo has no license): `.claude/concepts-from-fg-bot.md`. Catalog data sources, record structure, DB model and known data quirks: `docs/catalog-sources.md`. Design of the bot's guild/user/stock schema with the review decisions: `.claude/bot-schema-draft.md`. Step-by-step production deployment (VM setup, first deploy, Caddy, backups, updates, rollback, restore): `docs/deploy.md`. Open points (decisions and follow-ups the user schedules): `.claude/open-points.md`. What comes next (web app go-live, then the Discord ↔ web app integration: deep links, Activity, board): `.claude/handoff-golive.md`.

**Status:** the game catalog pipeline (extract → snapshot → import), the localization sources, an admin web UI (catalog browser, imports, read-only orgs/users overview with user data checks), the bot skeleton (router, registration, i18n), `/qm-setup` and the DB schemas for app and bot data exist. The stock service exists; UEX refinery data (community reports) is pulled into schema `ext` every hour; refinery jobs are limited to UEX refineries, the admin UI shows the data (tab 3rd Party), further processing is not built yet; the bot's commands are built (`/qm-setup`, `/qm-stock`, `/qm-refinery`, `/qm-bp`, `/qm-profile`: options search, modals ask, panels show), and so are the logs channel and the org board (one message per org, kept current; deep links from the bot into the web app's views). In production since 2026-10-05 (Docker Compose on a VM behind Caddy, see Deployment), not live for users yet: the production DB holds no real data so far. **Regular backups are not set up yet** (open TODO, `docs/deploy.md` § 6). Planned: a user web app with Discord login next to the admin UI (`docs/requirements.md`, "Web apps"). In progress: a companion desktop app (Tauri) that reads blueprint unlocks from `Game.log` and syncs the refinery jobs of a station with the terminal's work order overview (OCR on a screen capture, Windows only so far, in the player's language pack; the overview sync is not tested in game yet) through the user web app's API with the user's API token (see Architecture: companion app).

## Runtime conventions

- Backend: no build step. Node ≥ 22.18 runs `.ts` files directly via type stripping. Relative imports must use the `.ts` extension, and only erasable TypeScript is allowed (`erasableSyntaxOnly`: no enums, namespaces, parameter properties). TypeScript 7 for the backend.
- SPA (`adminapp/`): Vue 3 + Vite, own package with TypeScript 6 (`vue-tsc` needs the JS API that the Go-based TS 7 lacks). It imports shared pure code from `src/` (`src/adminapp/api-types.ts`, listed in `adminapp/tsconfig.json`); such files must not import server dependencies.
- DB sessions run with JIT off (`src/db/client.ts`): JIT compiled short list queries for ~450 ms each.
- `local/` is gitignored and holds the StarBreaker binary (`local/starbreaker`), snapshots, external `global.ini` files (`local/localization/<source>/`) and the extractor's working directory. Game data does not go into the repo. `assets/logo.png` is the app/bot logo (web copies: `adminapp/src/assets/logo-128.png`, `adminapp/public/favicon.png`, `webapp/src/assets/logo-256.png` for the user web app's login page, `webapp/src/assets/logo-{72,144}.png` for its Companion dialog, `webapp/public/favicon.png`, `companion/src/assets/logo-{44,88}.png` for the companion's title bar (exact sizes, Lanczos: the webview's own downscaling frays the edge); regenerate when it changes).
- Shell scripts must pass `shellcheck`.
- The checkout is shared by Linux and Windows (NTFS): `.gitattributes` keeps `*.sh` LF (Windows git has `autocrlf`), `core.filemode` is false (NTFS loses the executable bit), `node_modules` and `companion/src-tauri/target` are per platform (`pnpm install --config.confirmModulesPurge=false` after switching, full Rust rebuilds). File paths from module URLs only via `fileURLToPath` (`URL.pathname` is `/D:/…` on Windows).

## Deployment

- `Dockerfile` (multi-stage): one image for every process, the compose service's `command` picks it. Build stage with all dependencies builds both SPAs; the runtime stage has the backend's production dependencies only (`--filter sc-quartermaster`), `src/`, `drizzle/`, `adminapp/dist`, `webapp/dist`, runs as `node`. `package.json` must be in the image (`"type": "module"`). `.dockerignore` keeps `.env`, `local/` and `node_modules` out.
- `compose.yaml`: `db` (Postgres 18, no published port), `bot` (no port; `WEBAPP_ORIGIN` optional for its web app links), `ext` (the hourly third-party pull, no port), `admin` (the admin web UI, published on `127.0.0.1:3001` only), `webapp` (the user web app as `qm_web`, published on `127.0.0.1:3000` only, `WEBAPP_TRUST_PROXY=1`, the companion release mounted read-only from `local/companion/` of the checkout), `migrate` (profile `tools`, one-off). App containers run read-only, without capabilities, `no-new-privileges`; logs rotate (json-file with `max-size`: the default never rotates). Each service gets only its own variables; `DATABASE_URL` is built from the role passwords (URL-safe characters only). Never publish a port without `127.0.0.1`: Docker's port rules bypass ufw/firewalld.
- **DB roles** (`deploy/db-roles.sh`, idempotent): superuser `postgres` only for init, roles and dumps; `qm_owner` owns the database and everything the migrations create and is used by `migrate` only; `qm_app` (bot, admin, ext) has DML only, no DDL, `app.stock_journal` and `app.history` only `SELECT`/`INSERT` (append-only enforced by the DB), no access to schema `drizzle`, in schema `web` only column-level `SELECT` on `web.session` (`user_id`, Discord username/global name, `created_at`, `last_seen_at`, `expires_at`) and `web.api_token` (`user_id`, Discord username/global name, `created_at`, `last_used_at`) for the admin's user overview, never the token hashes (bot/admin must not forge web sessions; the bot shares the role, so it can read these columns too; regranted after the `REVOKE ALL` on every run, no migration involved). `qm_web` (user web app) reads `catalog`, `app` and `ext`, writes `app_user`, `stock_batch`, `stock_journal` and `history` (`INSERT` only) and `user_blueprint`, but `app.org`/`app.member` are read-only (no role IDs, no roster changes), no access to schema `bot` (revoked on every run, it read `bot.guild` until `0018`), full DML in `web`; its grants are explicit, reapplied on every run (default privileges cover `qm_app` only), identity inserts need no sequence grants. Grants for new tables come from `ALTER DEFAULT PRIVILEGES FOR ROLE qm_owner`, which only covers objects qm_owner creates: never run migrations as the superuser. The script runs on a fresh volume (mounted into `/docker-entrypoint-initdb.d/`) and in `deploy.sh` after every migration, fed via stdin: a single-file bind mount keeps the old inode after a push updated the checkout. On an SELinux host the mount needs `:z`. Migrations stay free of role names: dev and test DBs (`scripts/dev-db.sh`) run as superuser without these roles. A dump restores into a fresh volume (the init creates the roles first).
- Caddy runs on the VM host and terminates TLS: the user web app on 443 (`quartermaster.w00z.net` → `127.0.0.1:3000`, Caddy adds only HSTS: the app sets its own headers), the admin UI on its own port (`:8443` → `127.0.0.1:3001`), example in `docs/Caddyfile.example`.
- The scripts assume Docker Compose (as on the VM). podman-compose only serves for local tests and behaves differently: it does not wait for `service_healthy`, `run migrate` needs `--profile tools`, `up --wait` waits for every container of the project, and `up -d` does not recreate containers after the image changed.

## Architecture: catalog pipeline

```
Data.p4k --StarBreaker--> DataCore records (JSON) --normalize--> snapshot (.json.gz) --catalog:import--> Postgres "catalog"
external global.ini ------------------------------------------------------------------loc:import-----> Postgres "catalog"
```

Both imports also run from the web UI (upload, dry run first), using the same functions as the CLIs.

**The snapshot format (`src/catalog/snapshot.ts`, Zod) is the contract** between extractor and importer. It is versioned via `SNAPSHOT_SCHEMA_VERSION` (currently 3; an older snapshot must be extracted again); extractor implementations are meant to be swappable behind it (scunpacked-data is the documented fallback source). `src/catalog/import/load.ts` reads and checks a snapshot (gzip detected by content) for the CLI and the API.

**Extractor** (`src/catalog/extract/`): `cli.ts` shells out to the StarBreaker CLI (`p4k extract` for `Game2.dcb` + all `global.ini`, then `dcb extract --format json` for selected record subtrees; `--filter` globs match record *file paths*). `RecordStore` lazily reads records by lower-cased path; references between records are `file://…/libs/foundry/records/…` paths resolved via `refPath()`. `normalize.ts` must never crash on unexpected shapes: unknown types, `null` list entries and dangling references become `anomalies` in the snapshot. Items and manufacturers are only included when referenced by a blueprint. Locations are all `StarMapObject` records below `starmap/` (parent resolved to a UUID, type name from the inline types in `starmapobjecttypes.json`); the DataCore has no refinery or storage flag. An item's grade letter (A–D) and class (Military, …; Ballistic, Energy (Laser), …) exist only in its English description text and are parsed from there (the numeric record grade is set on every item, but only ship components have a grade in the game). Game build/channel come from `build_manifest.id` and the install folder name, not from a version string (the manifest has no "4.10.1").

**Catalog import** (`src/catalog/import/`): `plan.ts` is pure (snapshot → rows with content hashes, integrity check, diff, safeguard evaluation) and unit-tested without a DB; `apply.ts` runs everything in one transaction under a Postgres advisory lock (`IMPORT_LOCK`, shared with the localization import). A dry run executes the full import and then calls `tx.rollback()`; `noop`/`blocked` results also roll back. CLIs exit 0 (imported/dry run/no-op), 1 (error), 2 (blocked by a safeguard).

**Schema** (`src/db/schema/catalog.ts`, Postgres schema `catalog`, global for all guilds; migrations in `drizzle/`, `0000_catalog.sql` also seeds the app texts):
- Entity tables are keyed by the game's record UUID and carry `content_hash`, `first_seen_import_id`, `last_seen_import_id`, `retired_at`. Rows are **never deleted**: entries missing from a snapshot get `retired_at` (cross-checked against the diff), reappearing ones are revived. Future guild data must reference catalog UUIDs and survive retirement.
- `location` (star map objects) keeps every object; storage locations are selected by the app (`nav_icon` Station/LandingZone, not `hide_in_starmap`, name resolved). `parent_uuid` has no foreign key (import order), the integrity check covers it.
- Recipe tables (`blueprint_tier`/`_slot`/`_input`) are replaced as a whole when their blueprint's hash changes; the hash covers the full recipe.
- `raw_record` keeps every extracted DataCore record as `jsonb`, so new game data can be normalized later without re-extracting.
- Quantities are `NUMERIC` and passed to Postgres as strings.
- Localization: `localization_source` (source × lang × priority) + `localization`; the view `localization_effective` returns the highest-priority text per lang/key. Sources: `game` (priority 0, owned by the catalog import), external files (default 100, `loc:import`), `app` (1000, the app's own texts). Loc keys are stored lower case without `@`; texts have literal `\n` converted and "TRANSLATION NOT FOUND" placeholders removed. Some items have no name in any language → display code falls back to `class_name`.
- **App texts** (`src/catalog/labels.ts`): names the game lacks (blueprint category groups, item classes) live in source `app` under the reserved key prefix `qm_`. Both importers refuse the sources `game`/`app` and never take `qm_` keys from a file. Display names: game key `item_type<type>`/`item_subtype<subtype>` for types; `qm_blueprint_category_<group>` (category without size suffix, `blueprintCategoryGroup`) and `qm_item_class_<normalized class>` for app texts; otherwise a name derived from the technical key (`labelFromKey`). SQL helpers for these (`locText`, `categoryText`, `itemClassText`) are in `src/db/query.ts`.

## Architecture: web UI and crafting

- **API** (`src/adminapp/main.ts`, Hono): the admin web UI, one process, bound to `127.0.0.1` by default (in the container `0.0.0.0`, published on the host's loopback only), HTTP basic auth for everything (API and static SPA). Read endpoints under `/api` (`queries.ts`, response types in `api-types.ts`); writing endpoints (`/api/import/catalog`, `/api/import/localization`) take the file as raw body, are a dry run unless `dryRun=0`, and require the header `X-Quartermaster: 1` (CSRF protection: a foreign form cannot set it). Serves `adminapp/dist` with SPA fallback.
- **SPA** (`adminapp/`): look and building blocks taken from BindSight (design tokens, fonts, `Dropdown`, `ColumnHead` + `tableColumns.ts` resizable/sortable grid tables), shared classes in `adminapp/src/styles/ui.css`. GUI text is English and terse. Game texts follow the language picker (`lang.ts`). Catalog lists load completely and filter/sort in the browser; the text search runs on the server. Help texts live in `adminapp/src/help.ts` (`HelpTip`); technical values (keys, class names, hashes) are only shown in tooltips (`Tooltip`). Ordering rule: by priority where there is one, else by amount (largest first), else alphabetical. Item type icons: `adminapp/src/typeIcons.ts`.
- **User data** (`src/adminapp/users.ts`, read-only, tested in `test/admin-users.db.test.ts`): tabs Orgs (`GET /api/orgs[/:guildId]`: bot presence, settings, active/inactive members, batches shared there by active members, last history row naming the org; detail with the roster and the shared stock per material) and Users (`GET /api/users[/:userId]`: everyone in `app_user`, `web.session` or `web.api_token`; stored batches, SCU, pieces, refinery jobs, blueprints, last action (history as actor), last web login, companion token; detail with memberships, stock per material, running jobs, blueprints and the newest 20 history rows as actor, owner or recipient). Names (`userNames`): the newest web session's Discord profile, else the companion token's, else the org nickname, else only the ID (a user's name goes when their last session expires). Overview panel "User data checks" (`GET /api/checks`, every check listed also without hits): stock of retired materials, stock at retired locations, registered retired blueprints, refinery jobs ready for over 7 days (`OVERDUE_DAYS`), jobs outside the UEX refineries (none without UEX data). Needs the web column grants of `deploy/db-roles.sh` in production.
- **Crafting check** (`src/planner/`, used by the user web app only; the admin UI has none): `plan.ts`/`types.ts` are pure and shared by the web app's API and SPA (and later the bot): material totals with exact decimals (BigInt micro units), modifier curves per material quality, "N of M slots" choice, warnings. `load.ts` loads recipes from the DB. ASSUMPTION (unverified in game): modifiers of several slots on one stat multiply (`combine`).

## Architecture: user web app

In progress, plan and decisions in `docs/user-webapp-plan.md` (steps 1–3 built: schema/roles, backend foundation, SPA skeleton; plus realtime updates and the basic features: stock, refinery, blueprints, profile; compose service built, not deployed yet). Users without any org are first-class: every feature gets their path in the same step.

- SPA (`webapp/`): Vue 3 + Vite like `adminapp/`, imports the admin's styles and components relatively from `adminapp/src/` (no copies; `Icon.vue` is the only `v-html`, constants only, `test/spa-sources.test.ts` enforces it). UI texts de/en in `webapp/src/i18n.ts` (same keys enforced by type), language from `navigator.language` until picked. `session.ts` holds `/api/me` (401 = login screen); login is a plain link to `/auth/login`. The built SPA runs under the strict CSP (no inline scripts or styles; checked in Chrome).

- `src/webapp/` (Hono, own process, `main.ts`; `createApp` in `app.ts` builds the app without a server, the tests drive it via `app.request`). Middleware order: `secureHeaders` (strict CSP, no HSTS: Caddy sets it), own same-origin check for every non-GET (`Sec-Fetch-Site`, else `Origin` = `WEBAPP_ORIGIN`; Hono's `csrf()` only covers form content types), `no-store` on `/auth/*` and `/api/*`, `hono-rate-limiter` (in memory: `/auth/*` per IP, `/api/*` per session), then for `/api/*` the session check (401 for every route, unknown ones too), JSON-only writes (415) and a 16 KB body limit.
- Login (`discord.ts`): `openid-client` with hand-configured Discord endpoints (Discord is no OIDC provider; `arctic` was planned but is deprecated on npm), code + PKCE S256 + state, scope `identify`, redirect URI = `WEBAPP_ORIGIN` + `/auth/callback` (never from the request). State and verifier sit in the `__Host-qm_oauth` cookie (10 min); the Discord access token is used once for `/users/@me` and dropped. Failures redirect to `/?login=failed|denied`. Deep links: `/auth/login?returnTo=<path>` keeps the page the login started from (in the OAuth cookie; paths of this app only, never `//host` or a backslash: no open redirect) and the callback returns there; the SPA's login button sends the current path and query. The bot links `/stock?scope=<personal|all|guildId>`, `/blueprints?scope=<personal|guildId>`, `/crafting?add=<uuid>` (`webAppPath` in `src/bot/ui.ts`); each view reads its parameter once in setup (`takeQuery` in `webapp/src/deepLink.ts`, views only render after the login) and drops the query from the URL; an org the user is not in falls back to personal.
- Sessions (`session.ts`, `web.session`): 32 random bytes in `__Host-qm_session` (HttpOnly, Secure, SameSite=Lax), only the SHA-256 stored; 14 days idle, 30 days absolute; a login replaces this browser's session; validation re-creates a missing `app_user` row; expired rows deleted hourly. The Discord profile (name, avatar) lives in the session only, refreshed by each login; `/api/me` returns it for every user, also without any org (default avatar from the ID). Rights are never cached: `me.ts` reads the roster per request (active member rows; a server the bot left has none: `markGuildLeft`/`reconcilePresence` deactivate its members, migration `0018` dropped the former freshness mark `roster_checked_at`).
- **Features** (`routes.ts`, contract with all paths and shapes in `api-types.ts`): `GET /api/catalog?lang` (bookable materials with unit, locations with refinery flag and yield bonuses, blueprints, each material and location with its loc `nameKey` (the companion looks it up in the player's language pack); from the shared in-memory catalogs; no ores, no refining methods), stock (`/api/stock` personal = everything you own incl. shared, org = what its active members shared, with an owner filter, or `all` = both; writes `add`/`remove`/`adjust`/`move`), refinery (`/api/refinery/start|duration|done|remove`, always personal, always a work order: one station and an optional duration with 1–30 rows of a refined material, quality and expected yield; `duration` sets the time left later (end = now + seconds, null clears; for the companion too); `done` and `remove` take exactly the job's batches; yields are corrected through `/api/stock/adjust`), blueprints (own list, add/remove; default and retired refused), org members and their blueprints / owners of a blueprint (active members of the same org only), profile (`POST /api/profile`: RSI handle in `app.app_user`, the web app's own language override in `web.user_setting`, migration `0007`; the bot keeps its own in `bot.user_config`). Writes go through the stock service with an `Actor` from the roster; `guildId` in a write = the org context, needed only to share into it (add shared, move) and to give to its members (`toOwnerUserId`), and then you must be an active member there (403 `notMember`); remove/adjust/split/merge/share take none (your own batch; `share` checks each new org in the service). Errors: `{ error: code }` (`HttpError`; stock refusals 422 with the service's code). `expected` = the quantity the user saw (`batchChanged`). Lists answer exact decimals without trailing zeros and per-material totals (BigInt micro units).

## Architecture: third-party data (ext)

- `src/ext/` (own process, `main.ts`; compose service `ext`): `uex.ts` pulls `refineries_yields` (yield bonus in % per refinery terminal × ore) and `refineries_methods` (the 9 methods, ratings 1–3 only) from the UEX API (`api.uexcorp.uk/2.0`, bearer `UEX_TOKEN`) at start and every hour. UEX data are community reports, not game data; the game's DataCore has the method names only (`refiningprocess/*`), no factors, times, costs or location bonuses (server-side).
- `ext.snapshot` (`src/db/schema/ext.ts`, migration `0008_ext.sql`, written by `store.ts`): one row per `source` (`uex`), endpoint and distinct response (`data` as received, SHA-256 of it); a fetch with the same content as the endpoint's latest row only moves its `checked_at`, so the rows are the history of changes. Nothing references this schema.
- **Refineries** (`refineries.ts`): the terminals of the latest yields snapshot are matched to selectable catalog locations by English name within the same system (`(System)` and a trailing `Station` dropped; UEX has no UUIDs, the gateway names exist in two systems, the record keys are misleading). `refineStart` refuses other locations (`notRefinery`), the web app's refinery picker lists only these (`refinery` flag in `GET /api/catalog`); without any snapshot every selectable location counts. Yield bonuses are matched to catalog ores by `oreKey` of the English name (the game says "Hephaestanite (R)", "Raw Ice", UEX "Hephaestanite (Raw)", "Ice (Raw)") and kept for the ore's refined material: `yields` per location in `GET /api/catalog`, shown in the web app's refinery picker and on each running job ("Bonus +5 %"). Cached per snapshot ID and location/ore catalog.
- **Refining methods** (`ext.refining_method`, migration `0009_refining_methods.sql` seeds it): code (UEX's: DIN, FRX, …), the game's name key (`refinery_ui_processingtype_*`, localized through the catalog), yield %, seconds per SCU, source + game version (since `0015`: measured from in-game quotes at CRU-L1, 4.10.1; yield by the method's yield tier 31.5/38.25/45 %, time = 8 s/SCU × speed 1/2/6 × tier 1/4/16, the 8 s a stopgap: the measured base differs per ore, see `.claude/open-points.md`). Corrections only by a new migration. `refiningMethods(db, lang)` in `refineries.ts`, used by the admin UI only (no job estimates since the refinery books refined materials).
- Admin UI tab **3rd Party** (`ThirdPartyView.vue`, `GET /api/ext/uex`): pull status per endpoint, refinery terminals with their catalog match, yield bonus matrix, methods (UEX ratings and our community values joined by code).

## Architecture: stock

- **`src/stock/service.ts`** is the only code that writes `app.stock_batch` and `app.stock_journal` (shared by the bot and later the web UI): `add`, `refineStart`, `refineSetDuration`, `refineDone`, `refineRemove`, `remove`, `adjust`, `move`. Each runs in one transaction, locks the source batch (`FOR UPDATE`), compares amounts in SQL, deletes a batch at 0 (directly: an update to 0 violates `quantity > 0`) and returns the journal rows plus the resulting batch. Refusals are `StockError(code)`; callers map the code to a message.
- Rights live in the service, from an `Actor` (`userId`, the org `guildId` or null, `source`): **only the owner changes a batch** (remove, adjust, move, split, share, give; also without any org). Every batch belongs to one user (`owner_user_id`; the batch has no org columns since migration `0017`). **Sharing**: `share(batchId, guildIds)` sets the orgs the whole batch is offered in (`app.stock_share`, cascade-deleted with the batch; new orgs need the owner as an active member, taking back always works; history `share`/`unshare` per org). **Splitting**: `split(batchId, amount)` (unshared batches only, `sharedSplit` otherwise; less than all) moves a part into a batch of its own with a random `lot` (part of the merge key: new bookings go to the lot-less main batch). `move` changes the place (a lot stays a lot; a new target batch takes the source's shares, an existing one keeps its own) or gives (`toOwnerUserId`, an active member of `actor.guildId`; lands unshared in the recipient's main batch; history `give` with that org). The journal holds quantities only (no org columns; move/split/refine pairs share a `group_id`). Decided 2026-10-09, see `docs/requirements.md` "Stock"; the officer role is gone everywhere (migration `0016`). Refinery jobs are personal (also a CHECK) and hold **refined materials only** (no ores anywhere since migration `0025`, which converted running ore batches and dropped `refine_expected`): a job's batch is the material with its expected yield as quantity, **not stock yet** (`materialTotal`, the API's totals, the crafting check and the org board count `stored` batches only). A refinery job is a **work order** (migration `0013_refine_job.sql`): `refineStart` takes a station and an optional `durationSeconds` (→ `refine_ends_at`; `refineSetDuration` sets it later or clears it, no journal or history) for the whole job and 1–30 rows (resource, quality, expected yield as amount), journaled as `add`; every row is a batch sharing a new `refine_job` UUID (part of the merge key: the same material and quality within a job add up, other jobs stay apart) and the same start/end. A yield is corrected by `adjust` (history refinery adjust). `refineDone` takes the job ID and exactly its batches (else `batchChanged`), each with the amount handed out ("0": nothing stored): each batch becomes `stored` at the same place and quality (merging into an existing batch), one journal group per job (`refine_out`/`refine_in`). `refineRemove` (a job that will not come out) takes exactly its batches too and removes them (journal `remove`, history refinery remove). `(state = 'refining') = (refine_job IS NOT NULL)` (CHECK); stored batches have every job field NULL. The job fields are not part of `BatchKey` and not journaled; `loadBatches` returns them as `refine`.
- Bookable: resources used in a recipe and items used in a recipe (never ores); not retired; locations per `selectableLocationSql()`. Optional `expected` (the quantity the user saw) aborts with `batchChanged` instead of booking against a changed batch.
- `src/stock/lookup.ts` (no Discord, also for the web UI): `locationCatalog` (selectable locations with label "Name · planet/moon · system" and `short`, the name plus the system where it is ambiguous, e.g. gateways) and `materialCatalog` (bookable materials), both with `nameKey` and cached per language and reloaded after a newer catalog import; `pickableBatches(actor, pick)` (the actor's own batches, shared or not; `move` without refinery jobs, `refining` only own jobs; ordered by material, then quality descending); `searchWords` (all words, prefix of the name first). `src/bot/pickers.ts` builds the Discord autocomplete choices from these (`batchLabel`: "⚗️ Material · Q820 · 12.5 SCU · Location · Org (Holder)").
- `src/stock/amount.ts`: `parseAmount` (SCU with point or comma, up to 6 decimals; items whole pieces; validated as text, never as float), `formatAmount` (NUMERIC text without trailing zeros).

## Architecture: bot

- **Schemas** (migrations `drizzle/0002_app_bot.sql` to `0007_user_setting.sql`; `0006` adds the change triggers, see Architecture: user web app; `0009` the refinery job columns of `stock_batch`, `0013` the work order ID `refine_job`, `0014` drops `refine_method`, `0025` `refine_expected` (jobs hold refined materials), see Architecture: stock): `app` (`src/db/schema/app.ts`) holds the data the bot and later the web UI manage: `org` (one per server, member role IDs), `app_user` (global per user), `member` (user × org, roster; PK `(guild_id, user_id)` is the FK target for stock and journal), `stock_batch` (one row = one batch of one owner, merge key `UNIQUE NULLS NOT DISTINCT` incl. `refine_job` and `lot`, deleted at 0; global per user, no org), `stock_share` (batch × org it is offered in, since `0017`), `stock_journal` (append-only, copy of the batch key without the lot, `group_id` for move/split/refine pairs, no org), `user_blueprint` (per user; default blueprints are not stored). `bot` (`src/db/schema/bot.ts`) holds bot-only configuration and state: `guild` (base language, `#logs` channel + level, board channel/message/style/title/subtitle (`0021`–`0024`), presence: `left_at` set on `GuildDelete`, cleared on `GuildCreate`, reconciled with the guild cache on `ClientReady`), `user_config` (language override); `guild.logs_after` marks the last `app.history` row the logs channel handled (migration `0020` replaced the unused `logs_outbox`). `web` (`src/db/schema/web.ts`) holds the user web app's state: `session` (SHA-256 of the cookie token, Discord username/global name/avatar hash as of the login, no FK to `app_user`, deleted when expired), `user_setting` (the web app's language override, no FK). `bot` and `web` reference `app`, never the other way round. Discord IDs are `text` with a format CHECK. Nothing is deleted except batches at 0. Rules a CHECK cannot express (crafting inputs only, refinery jobs only at refineries, selectable non-retired locations) live in the stock service (see Architecture: stock).
- **Migrations applied in production are frozen:** never edit, regenerate, reorder or delete them; every schema change is a new migration. drizzle only compares the timestamp of the last applied migration (the stored hash is never checked): an edited migration, or one with an older timestamp than the last applied, is skipped silently. Dev/test DBs may still be reset. Production updates run through `scripts/deploy.sh` (see Deployment).
- `src/bot/`: `main.ts` (client with intents `Guilds` + `GuildMembers` (privileged, enabled in the developer portal), DB connection, routes `InteractionCreate`, member events → roster), `interactions.ts` (router), `registry.ts` (`BotCommand`: registration JSON + `execute`/`autocomplete`/`component`/`modal`, `modalSubcommands`, `ephemeral` defaults to true; `bySubcommand` dispatch; handlers get `db` in their context), `ui.ts` (`customId` (checks Discord's 100 characters), `panel` (Components V2 reply), `webAppButton`/`webAppRow` (link from `WEBAPP_ORIGIN`, none when unset; a path from `webAppPath` makes it a deep link, an optional label), `textField`/`textValue` for modals), `lang.ts` (the user's language), `commands.ts` (the command list), `commands/*.ts` (one file per root command), `register.ts` (bulk overwrite — an empty list removes all registered commands), `errors.ts`, `i18n.ts`.
- **UI model** (`docs/requirements.md` "Bot interaction"): options are only what has to be searched (autocomplete, at most two), everything typed comes in a modal opened right after the command, lists and results are ephemeral panels (Components V2, `ReplyContent.flags` = `IsComponentsV2`, the router adds Ephemeral). Submitting a modal books (it is the confirmation; the amount it showed goes along as `expected`); the refinery start has a preview first. Results take 2–3 lines and repeat nothing (what happened · the batch now, its amount only where it differs from the booked one · small: the material in your stock, only where more than this batch).
- The router defers a command that has not replied after 2 s (Discord's limit is 3 s), **except subcommands listed in `modalSubcommands`** (`''` = a command without subcommands): a modal is only allowed as the first answer, so those must answer within 3 s (only cached lookups and single-row reads before `ctx.showModal`). Handlers reply via `ctx.reply` only, never `interaction.reply` directly: it picks reply, edit of the deferred reply or follow-up.
- Components and modal submits are routed by custom ID `<command name>:<rest>` to that command's `component` / `modal` handler, which answers with `interaction.update` (redraw the panel; a modal opened from a panel button can update it too) or a reply. A modal submit cannot open another modal: more steps go through a button. Errors after a `deferReply` land in that reply. Context of a modal (batch ID, shown amount, target) travels in its custom ID; only what does not fit sits in `state.ts`.
- All root commands are prefixed `qm-`. `/qm-setup` (`commands/setup.ts`, `settings.ts`): admins only (`default_member_permissions` Manage Server plus an own check on every interaction), an ephemeral Components V2 panel (a plain message allows only 5 rows; one section per area: 👥 members, 🌐 language, 📜 logs, 📋 board, each with its heading and controls, separated by lines; the text repeats no setting the selects show, only a short line on what language, logs and board are for and the channel checks) with six selects (member roles, base language, `#logs` channel, logs level `off`/`org`, board channel, board style `list`/`table`) and a "Board title" button (modal: title, empty = the org name, and an optional subtitle, 100 characters each), each change is saved at once and redraws the panel; shows whether the bot has View/Send/Embed/Attach in the `#logs` channel and View/Send in the board channel. A change of language, board channel, style or title asks the board poster to render that board again (`requestBoardUpdate`).
- **Roster** (`roster.ts`): `app.member` rows exist only for current holders of a member role (bots never). Losing the role or leaving the server deletes the row unless stock or journal rows reference it, then it stays with `active = false`; the `app_user` row goes too, but only once it holds no data at all (no member row, blueprint, personal stock, journal row, RSI handle or `bot.user_config`): users can work without any org. **`roster-keeper.ts`** (`RosterKeeper`, wired in `main.ts`) keeps it current (no freshness mark since `0018`: membership is the active row). Full syncs on `ShardReady` and on `ShardResume` (discord.js drops the member events Discord replays before RESUMED), on joining a server, on `GuildAvailable` after an outage, after role changes in `/qm-setup` (`requestFullSync`), when a configured role is deleted, every 6 h as a backstop, and 5 min after a failed sync or member event. Per guild, full syncs and member events (`GuildMemberAdd/Update/Remove`) run one after another (a sync working from an older member list must not overwrite a newer event); a sync request while another one waits joins it; member list fetches of a guild are at least 31 s apart (Discord rate-limits gateway opcode 8 to about one per 30 s). The bot leaving a server (`GuildDelete`, or found gone at start) deactivates its members: the org is gone for them until a sync after the bot came back. The caller's row is also synced on every `requireMember` call (live data, outside the queue). Servers without `/qm-setup` have no org and no roster.
- **Access** (`access.ts`): `requireMember(db, interaction)` for every command that needs org membership: refuses outside servers, before setup (`error.notSetUp`) and without a role (`error.notMember`); returns the member flag and the settings, resolved live from the interaction. Admins (Manage Server) are not members by that alone.
- **`/qm-bp`** (`commands/blueprints.ts`, `blueprints.ts`): add/remove/list/who; list (20 per page) and who (60 names per page) are panels, paging in the custom ID. The blueprint catalog with display labels is cached in memory per language (`importCache` in `src/db/import-cache.ts`, shared with the stock lookups: reloaded when a newer catalog import exists, checked at most once a minute) because autocomplete must answer within 3 s; autocomplete values are blueprint UUIDs, free text that was not picked is refused. Autocomplete handlers get `(interaction, lang, db)` and must not write (no roster sync there).
- **`/qm-stock`** (`commands/stock.ts`): `add material location` (modal: amount, quality, "Share in" checkboxes of your active orgs, this server's ticked; the batch it lands in keeps its shares, the ticked ones are added via `share`), `remove|adjust|share batch`, `move batch to`, `give batch member` (own roster autocomplete, active members only; give labels leave the shares out), each a modal with the batch as its head and the amount prefilled ("all", adjust: the current amount, "0" allowed); `list [material]` (panel: Personal / this org / All, 20 lines per page, state in the custom ID) and `find material [min_quality]` (panel). The booking logic (`bookAdd`, `bookChange`, `bookShare`, `listLines`) takes no Discord objects and is tested on its own. `StockError` codes map to `stock.err.<code>` texts. Splitting and merging are not in the bot.
- **`/qm-refinery`** (`commands/refinery.ts`, pure parsing in `refinery-lines.ts`; personal, no member role needed): `start station` (modal: optional duration, material lines `<name> <quality> <yield SCU>` read from the right, resolved with `findMaterial` from `src/stock/material-names.ts` (exact name, else a unique prefix) over the resources in de and en) → preview panel (Register / Edit / Cancel, draft in `state.ts`), `time job` (time left, empty = open: `refineSetDuration`), `done job` (modal prefilled with "Name quality: yield" lines, checked in order; stores the job), `remove job` (a confirm panel naming the job, Remove / Cancel, draft in `state.ts`: `refineRemove` with the batches and amounts shown), `list` (panel). No ores, no refining method, no estimates.
- **`/qm-profile`** (`commands/profile.ts`, `profile.ts`; no org needed): modal with RSI handle (same rule as the web app) and language (radio: follow Discord / English / Deutsch); the `app_user` row is only created when there is something to store.
- **Logs channel** (`logs.ts`, `LogsPoster` started on `ClientReady`): polls `app.history` every 30 s per server with a channel and level `org` (`logRows`: share/unshare/give with `guild_id` = the server, and stock add/remove/adjust/move/merge/give whose `details.sharedIn` holds it; the service records `sharedIn` = the orgs a batch was shared in when it changed). One line per row in the server's base language (`logLine`, people as mentions, `allowedMentions` none), packed into messages of ≤ 2000 characters (`messagesOf`); then `logs_after` moves forward (only if `/qm-setup` did not reset it meanwhile). A new channel or level sets `logs_after` to the newest row (`updateGuildSettings`), so the past is never posted. Discord errors other than an unusable channel (unknown, no access, missing permissions) are retried next round; an unusable channel's lines are skipped.
- **Board** (`board.ts`, `BoardPoster` started on `ClientReady`): one message per org in its board channel (`/qm-setup`), edited in place, in the server's base language: title (`board_title` or the org name) with the server icon (gateway cache) as thumbnail and the optional subtitle, the figures of the web app's org tile (members, blueprints X / obtainable, resources and items with kinds and locations; `orgMetrics` in `src/stock/org-summary.ts`, shared with `/api/summary`), the shared materials per kind (`orgMaterials`: total, best quality with its level (`qMark`, `src/stock/quality.ts`, shared with the SPA), holder count, always plural; the 10 largest per kind, "+n more"), buttons "Show all" (`qm-stock:org`: the org list panel, ephemeral, member check) and deep links Stock/Blueprints, "Updated <t:…:R>". Style `list` (text lines, ⛏️/📦 headings) or `table` (code-block tables: amounts right-aligned, the stars last because their width differs between fonts, names cut at 22 characters, backticks replaced). Only stored stock shared in the org by active members; never unshared stock, refinery jobs or holder names. Rendered only for orgs marked as changed: the bot holds `LISTEN qm_changes` (`listenForBoardChanges`; the web app's triggers: `stock`/`member`/`org` with an org mark it, `blueprint` marks every org of its user), `/qm-setup` marks directly, a newer catalog import, the start and every listener reconnect mark all; every 30 s the marked ones are rendered and compared with what was shown (in memory: a restart edits each board once), edited only on a difference; a deleted message is posted again (its ID stored only while the channel is unchanged); network/5xx errors retry next round, an unusable channel waits for the next change. Another board channel gets a new message, the old one stays where it was.
- `state.ts`: short-lived per-user state behind buttons whose data does not fit into a 100-character custom ID (the refinery drafts; in memory, 10 min).
- `UserError(key, vars, { webApp })` → friendly ephemeral message in the user's language, not logged (`webApp`: with the web app link; set by `requireMember` for "not set up" and "not a member"); any other error → generic message + log.
- Bot UI texts are de/en dictionaries in `i18n.ts` (same keys enforced by type and test); game texts come from the catalog. Command names are English, descriptions localized (`localizedDescription`; Discord shows them in the client's language, the bot's language override cannot change that). Private output follows `lang.ts`: the `/qm-profile` override in `bot.user_config` (cached in memory, written through `setLangOverride`), else `userLang(interaction.locale)`; public output (the logs channel) uses the server's base language from `bot.guild` (never Discord's guildLocale).

**Tests** (`test/`): `fixtures.ts` builds synthetic DataCore records (no real game data) and runs them through the real normalizer; the resulting snapshot feeds both the pure tests and the DB integration tests.
